## watched 车型位图受 64 位上限约束

`RepairCell::watched_vehicles`（`algorithm/include/algo_alns_repair.h:91`）用 `std::uint64_t` 记录「评估时可行、但因车型被占满而跳过的更便宜车型」，只有 64 位；车型数超过 64 时按下标 % 64 分桶，同一桶的车型共用一位，某些释放会触发本不必要的重评估（每格一次完整 `evaluate_insert`），桶越粗（车队规模远大于 64）多触发越明显。异构大车队下，每次 commit 换车触发的 release 都可能放大成多余的格重评估。

现状不会越界：置位与匹配的位移统一取 `(unsigned)vehicle_ind & 63`（`algorithm/src/algo_alns_repair.cpp:444`、`problem/src/prob_load_editor.cpp` 的 `evaluate_insert`），不会出现位移量 ≥ 64；问题只在于桶粒度带来的多余重评估。

未直接改用 bitset 的原因：`std::bitset<64>` 与 `uint64_t` 等价，固定宽度的 `bitset<N>` 只是更换上限；每格动态位图（`std::vector<uint64_t>` 等）会让 `RepairCell` 失去 POD 性质并在热路径 `eval_cell` 上引入每格分配。

可选方向：

- 已采用临时方案（2026-11-28）：位图按下标 % 64 分桶，置位与匹配统一用 `& 63`；`RepairCell` 仍是 32 B POD，零额外内存，release 触发的重评估量约为精确方案的 ⌈N/64⌉ 倍；
- 若车队规模可能上千（桶过粗），改为按车型维护「待重评估格子列表」，精确且无上限，但需要解决 init 并行阶段 `eval_cell` 不能写共享列表的问题（先写格内索引、串行阶段汇总）。
