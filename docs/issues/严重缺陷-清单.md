
## 时间窗推导缓存 `NodeTimeWindowCache`

**简介:**

`Node::intersection_time_windows()` —— 把 node 内所有 activity 所属订单的时间窗求交集，得到该 node 的可行时间窗集合。

**当前状态**：每线程一份缓存。

**设计缺陷清单:**

**1) 缓存受线程束缚**

缓存生命周期绑定 `std::thread::id` `LoadContext::thread_tw_caches` 线程池每次重建 → 新 thread id 查不到 → **全部冷启动**；旧线程的缓存留在 map 里直到 LoadContext 析构（每次 alns 累积 9 份）。

**2) other_cache 的过度设计**

`other_cache` 用哈希表是过度设计 | `get_other_time_windows` | 键空间只有 `(type, loc)`，实测**全进程仅 2 个有效 key**（START / END 哨兵），却被调 **756 万次**。miss 18 次（9 线程 × 2）。 |

## 相关：`ThreadPool` 生命周期与并发度

A1 把缓存绑在线程上之后，线程池的生命周期就成了缓存命中率的前置条件。

### 现状

`ThreadPool` 是 `solver/src/stra_strategy.cpp:79` 里 **`alns` lambda 的栈局部变量**：

```cpp
this->lua.set_function("alns", [workspace](const sol::table& cfg) {
  ThreadPool thread_pool;      // ← 每次 alns() 新建 8 个线程
  ...
});                            // ← 结束即 join，线程销毁
```

线程销毁 → `std::thread::id` 消失 → 下次 `alns` 的新线程在 `thread_tw_caches` 里查不到 → **每线程一份缓存全部冷启动**；旧缓存不回收，每次 `alns` 累积 9 份。

**但目前不受影响**：`case1/strategy.lua` 只调 1 次 `alns(50 iter)`，冷启动被 50 轮摊薄。**一旦变成"按标签分区、每分区一次 alns"（DSL 明显的设计意图），冷启动就会主导耗时。**


### 屏障语义（已确认，可用于"两级缓存"类方案）

`algo_thread_pool.cpp` 中 `parallel_for` 返回前 `cv.wait` 等待 `finished_worker_count == worker_count`，是**真屏障**。因此"并行阶段只读 → barrier → 单线程写全局 → 下一轮并行只读"在内存模型上安全（并发 const 读无写者不构成 data race；barrier 的 mutex 提供跨轮可见性）。
